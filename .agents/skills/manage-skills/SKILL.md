# スキルを探す・作る・育てる

ユーザーの繰返し作業や判断を支援する仕組みを整える。既存スキルの導入と自作を対等な選択肢として扱い、実際の用途に合う最小限の構成を選ぶ。

## 最初に確認すること

依頼と既存資料から、次を把握する。既に分かることは聞き直さない。

- **用途**：どんな依頼で使い、何を成果物にするか。
- **適用範囲**：全プロジェクト共通か、特定プロジェクト・ディレクトリ向けか。
- **再利用する知識**：通常の能力だけでは不足する判断基準、手順、資源は何か。
- **制約**：必須の形式、利用環境、変更してはいけないものは何か。

関連する `AGENTS.md`、導入済みスキル、プロジェクト内の手順・資料を先に確認する。内容が足りていれば、外部検索や詳しい聞取りを必須にしない。

## 再利用・作成・ルール化の選択

| 状況 | 選ぶ対応 |
|---|---|
| 導入済みスキルが目的を満たす | 既存スキルを使い、重複を作らない |
| 既存スキルの用途は同じで、具体的な不足がある | そのスキルを限定的に改善する |
| 一般的な作業で、良い既存スキルがありそう | 適切な範囲で探索し、内容を評価する |
| 独自の判断基準・作業手順・資料が必要 | 自作する。外部検索を作成の前提にしない |
| 常に守る短い指示 | 適用範囲に合う `AGENTS.md` に記す |
| 詳細な仕様・設計・調査結果 | 既存の文書置き場に保存し、必要箇所から参照する |
| 一回限りの要望で、再利用する手順がない | 今回の依頼内で扱い、永続化しない |

人気や自作へのこだわりより、適合性、理解・保守のしやすさ、依存の少なさを重視する。探索して候補が合わなければ、理由を説明して作成へ進む。検索を繰り返すだけで終えない。

## 汎用スキルとプロジェクト固有スキルの分け方

配置の基本方針は `~/.codex/AGENTS.md` を正本とし、ここでは分類・分割時の判断を示す。対象プロジェクトの場所と既存構成を確認してから配置する。

### 内容から適用範囲を判断する

「別のプロジェクトでも、固有の設計や環境を知らずにこの手順を使えるか」を確認する。ファイル名や絶対パスを消すだけで汎用化できたとは扱わない。

| 判断対象 | 汎用側に置くもの | プロジェクト側に置くもの |
|---|---|---|
| 研究 | 問い・仮説・反証・対照実験の立て方 | 対象手法の成立条件、固有の実験手順 |
| 報告 | 結果・根拠・限界の示し方、図表の形式 | その研究の方式名、測定値、専用の出力先 |
| 実装・検証 | 他の対象でも成立する調査・検証の方法 | 対象のABI、再配置、コード経路に依存する検証 |
| 言語・設計 | プロジェクトに依存せず独立して使える手順 | 採用言語の版、独自仕様、設計判断、不変条件 |
| 環境 | 特定環境を前提にしない作業方法 | カーネル設定、機器、パス、ビルド・実行条件 |

専門的な内容でも独立した用途と再利用性があれば汎用スキルになりうる。ただし、複数の関連プロジェクトで使うという理由だけで、固有の設計に依存するスキルをユーザー共通の場所へ置かない。判断がつかない場合は元の適用範囲を保ち、汎用化に必要な条件を確認する。

### 常時必要な指示と作業手順を分ける

プロジェクト側の内容も、すべてスキルに入れない。

- どの作業でも守る言語の版、設計制約、基本コマンドは、プロジェクトの `AGENTS.md` に短く記す。
- 特定の実装・調査・実験を行うときの判断基準や手順は、プロジェクトの `.agents/skills/` に置く。
- 詳細な仕様・設計の説明や実験結果は既存の文書置き場へ置き、指示側から必要な場面を示して参照する。

### 混在したスキルを分割する手順

1. 本文だけでなく、参照資料、スクリプト、素材、依存する環境を確認する。
2. 各内容を、再利用できる方法、対象固有の手順、常時適用する指示、参照資料に分類する。
3. 共通部分を受け持つ既存スキルがあればそこへ統合する。まとまった独立用途がある場合に新しい汎用スキルを作り、わずかな一般論だけのスキルは増やさない。
4. 固有側には対象、適用条件、固有の手順と制約を残す。共通側の本文をコピーせず、必要な箇所だけ参照する。
5. 移動先の利用可能性と参照元を確認してから、不要になった重複を除く。異なる内容の同名スキルが既にあれば、上書きせず差分を確認する。
6. 形式、リンク、依存ファイル、呼出し名を確認し、どのプロジェクトで適用される構成になったか報告する。

プロジェクト単独での共有・利用が必要なら、ユーザー個人の共通スキルが必ず存在する構成にしない。依存スキルの用意方法や共有元を明示する。複数プロジェクトで固有スキルを共有する場合も、正本を一つにし、利用するプロジェクト側から参照・リンクする。ユーザー共通の探索場所へリンクして、意図せず適用範囲を広げない。

### 配置例

```text
~/.agents/skills/
├── research-report/         # 汎用の報告方法
├── grilling/                # 汎用の批判的な問答
└── manage-skills/           # 汎用のスキル管理

<project>/
├── AGENTS.md                # 基本条件・設計制約・資料への案内
├── .agents/skills/
│   └── helper-inlining/     # 対象実装のインライン化・検証手順
└── docs/                    # 既存構成に従う仕様・設計・実験資料
```

この例を理由に、実在しないスキルや不要な文書を作成しない。特定の研究で見つけたスキルを共通側へ取り込む依頼でも、内容を評価し、固有のまま取り込まずに汎用部分だけを抽出する。固有スキルを共通側から外す依頼では、プロジェクト内の原本まで削除しない。

## 既存スキルを探す場合

まずローカルの関連スキルを確認する。外部探索が必要なら、skills.sh、提供元のリポジトリ、利用可能な検索手段を使う。検索語には対象分野と具体的な作業を含める。

Skills CLIが利用できる場合の例：

```bash
npx skills find [query]
npx skills add <owner/repo@skill>
```

CLIの提供状況やオプションに不確かさがあれば、実行前にヘルプや公式資料を確認する。保存先は共通方針と依頼に合わせ、無条件にグローバル導入しない。

候補は検索結果だけで推薦せず、`SKILL.md`と関係するスクリプト・依存関係を読んで評価する。

- 依頼した作業と適用範囲に合っているか。
- 有用で具体的な判断基準や手順があるか。
- 不要な権限、外部送信、依頼外の操作を要求しないか。
- 利用環境、依存ツール、保守状況、ライセンスが用途に合うか。
- 既存のルールやスキルと矛盾・重複しないか。

導入数やスター数は補助情報とし、固定の件数で品質を判定しない。推薦時は用途、適合する理由、制約、提供元のリンクを短く示す。導入が依頼されていれば、説明だけで止めず、その範囲内で導入と確認まで進める。

## 新規作成・改善の進め方

利用可能なら `skill-creator` を読み、作成・更新・形式検証の手順に従う。このスキルは何を作るかと配置を判断し、作成の詳細は `skill-creator` に任せる。利用できない場合も、以下の基本構成で小さく作れる。

### 1. 用途と境界を定める

実際に受けたい依頼を具体化し、期待する成果物と完了条件を決める。隣接する既存スキルと混同しそうなら、対象外も明示する。

一つのスキルに、関係の薄い作業をまとめない。反対に、同じ目的のわずかな違いごとにスキルを増やさない。実際の使われ方と必要な文脈で分ける。

### 2. ルールを設計する

- **必須事項**：正しさやユーザー指定に直結する制約。なぜ必要か、いつ適用するかを明確にする。
- **判断指針**：状況に応じて選べる基準。例を唯一の正解や固定手順にしない。
- **参照情報**：詳細な仕様・例・手順は必要な場面だけ読む資料に分ける。

エージェントの判断や成果を実際に改善する内容を残し、一般論や既存指示の言い換えを増やさない。固定の反復回数、ツール、形式、承認手順などは、ユーザーの指定や具体的な必要性がある場合に定める。

過去の一度の失敗、特定環境の事情、好みを、全プロジェクトの必須ルールに広げない。未確認の仮説は確定したルールにしない。矛盾する既存ルールを見つけたら、適用範囲を確認し、どちらかを黙って上書きしない。

### 3. 適切な場所に実装する

`~/.codex/AGENTS.md` の配置方針に従う。ユーザー指定の保存先があれば優先する。

- 汎用スキル：`~/.agents/skills/<skill-name>/`
- プロジェクト固有スキル：`<project>/.agents/skills/<skill-name>/`
- 常時適用する基本ルール：共通またはプロジェクトの `AGENTS.md`

スキル名は小文字の英数字とハイフンで付け、フォルダ名と一致させる。説明・本文は日本語を基本とし、識別子やコマンドは原表記を保つ。既存スキルの名前は、用途拡張だけを理由に安易に変更しない。

最小構成は `SKILL.md`。冒頭のYAMLには `name` と、用途・適用条件が分かる `description` を記す。本文には判断基準、必要な手順、成果物、完了条件を記す。短いスキルのために不要な補助ファイルを作らない。

必要な場合だけ、詳細資料を `references/`、繰り返す処理を `scripts/`、成果物用素材を `assets/` に追加する。参照資料には読む条件とリンクを付ける。原本を一つにし、汎用と固有のルールを重複管理しない。

### 4. 確認して仕上げる

形式検証を行い、適用条件、配置、参照先、依存先、未完成の雛形がないことを確認する。スクリプトを追加・変更した場合は、目的に合う入力で実行して確かめる。

内容面では、実際に想定する依頼に適用できるか、似ているが対象外の依頼まで拾わないかを確認する。形式検証の成功だけで、有用性や動作を検証済みとしない。高度な評価は複雑さと影響に応じて選び、小さな文書変更に大掛かりな試験を課さない。

完了報告では、変更先、できること、使い方、実施した確認、重要な未確認事項を簡潔に伝える。提案を求められただけなら提案を返し、作成・改善を依頼されていれば実際のファイルまで仕上げる。

## 相談する場面

次のような、成果に影響する未決事項を資料や依頼から判断できない場合は、理由と選択肢を添えて簡潔に尋ねる。

- 汎用ルールかプロジェクト固有ルールかで、適用範囲が大きく変わる。
- 複数の報告形式や作業方針に、ユーザーの好みの選択が必要。
- 既存ルールとの矛盾があり、どちらを維持するか判断できない。
- 自動実行の範囲や外部への操作など、依頼から権限を判断できない。

軽微な命名、章立て、補助資料の分け方は合理的に決める。既に承認された方針や分かっている情報を聞き直さず、回答に依存しない調査・整理は続ける。

## 利用後の改善

実際の利用で見つかった不足を、具体的な事例と期待動作に結び付けて直す。追加だけでなく、重複や役立たない指示の削除も検討する。ルールの適用範囲を広げる変更では、他の用途への影響を確認する。通常の作業中に得た知見を、依頼なく永続ルールへ自動追記しない。
