# 性能測定と実装の対応

## 比較可能性を先に確かめる

CPU・OS・ソースcommit・コンパイラ・ビルド設定・入力・実行経路を確認する。変更対象以外の条件が異なる測定を、そのまま提案手法の効果として扱わない。カーネルやコンパイラを変更した場合は、必要に応じて同じ環境で基準方式も測り直す。

同じ戻り値でも、早期終了、失敗経路、汎用dispatch、定数化などの処理内容は異なりうる。「同じ処理」の意味を、同じ入力・出力なのか、内部処理も同じなのかに分ける。成功経路を測っていない実験から成功時の性能を一般化しない。

性能測定前に期待結果と実際の適用状態を検査する。最適化を有効にする設定だけでは適用の証拠にならない。フォールバック、残ったcall、実際の呼出し先も確認する。

## 測定単位と統計

- プログラム1実行、helper1反復、システムコール1回など、時間の単位を明示する。ループ全体の時間を反復数で割った値には周辺処理が含まれることがある。
- 測定内部の大量反復と、独立した起動・ロード・試行を分ける。内部反復を全て独立標本として区間を過度に狭めない。
- 同じ起動内で比較した設計なら、対応差の集計を検討する。起動数や区間推定法を固定の慣例として押し付けない。
- 実行順序、ウォームアップ、CPU固定、乱数seed、PMU多重化などは、今回の差に影響するものを記載する。
- パイロット、無効な測定、本測定を区別する。除外は遅い値を都合よく捨てるために行わず、条件違反などの理由を残す。

短縮率は `(基準時間 − 比較時間) / 基準時間 × 100`。時間比は `比較時間 / 基準時間`、速度比は `基準時間 / 比較時間` で異なる。平均の比と比の平均も区別する。小さな分岐予測ミス数などは割合だけを示すと誤解を招くため、絶対差も示す。

## 生成コードを説明する場合

まず処理経路を確定する。例えば「ソース → LLVM出力 → verifierによる書換え → JIT → 実行時パッチ」のどこで差が生じたかを調べる。全てをJITやコンパイラの選択と一括りにしない。

比較する証拠は、該当するものを選ぶ。

| 資料・指標 | 分かることと注意点 |
|---|---|
| ソース・コンパイル条件 | 入力と最適化の前提。これだけでは実行コードを確定できない |
| 中間表現・bytecode | 操作が分解・置換された段階 |
| 実行時機械語 | 実際の命令選択、内部call、分岐、レジスタ保存 |
| 静的命令数・コードサイズ | 配置されるコード量。未実行経路やpaddingを区別する |
| PMUの実行命令数・分岐数 | 通った経路の動的な仕事量。採取範囲を記載する |
| 時間・cycles | 実際の性能。単独では原因を特定できない |

本文では同じ処理範囲の短い抜粋を並べ、完全な逆アセンブルは付録へ置く。省略したprologue、epilogue、stack補正、内部callを明記する。call除去による差と、本体の命令選択による差を混ぜない。

コピー・再配置を検証する場合は、意図した関数範囲と埋込み領域の全体を検査する。短い一致部分だけでは、隣接コードの混入や余分な命令を見逃す。期待されるアドレス修正・出口の変換と、意図しない差を区別する。

「分岐予測が効いた」「乗算が重い」「キャッシュの効果」などは候補であり、命令列だけから確定しない。依存関係、メモリアクセス、spill/reload、コード配置、定数化、直接・間接呼出しの差を、必要な対照と測定で切り分ける。

## 再現資料

既存の構成に合わせ、生データ、集計、入力、実装差分、設定、ソース版、使用コマンド、必要な生成コードを紐付ける。図表の行から対応する条件・実行へ辿れる識別子を保つ。巨大なイメージを必ず配布する必要はなく、再ビルド方法と識別情報で補える場合はその範囲を説明する。
