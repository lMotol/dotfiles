# 研究レポートサイトの運用

報告時点の知見を日付付きの記事として蓄積する。読者が今回の報告を単独で理解でき、過去の経緯も追えるサイトにする。本文、要約、案内は日本語を基本とし、正式名称やコード識別子は原表記を保つ。

## 役割と適用範囲

このスキルは記事の追加単位、日付、過去記事の保存・訂正、記事間の参照、一覧の運用を定める。

- 研究内容の執筆・根拠の整理が必要な場合は、利用可能な [research-report](../research-report/SKILL.md) を併用する。完成原稿の掲載だけなら分析をやり直さない。
- 表示を新設・変更するときは [Web研究記事の表示指針](../research-report/references/web-report.md) を読む。既存の読みやすい見た目を保つ。
- 公開する場合は、利用する環境の現行手順に従う。Sitesを使う作業では利用可能なSitesスキルを読む。このスキルだけで公開先・公開範囲・権限を決めない。
- 特定の研究テーマ、サイトID、保存パス、測定値をこの汎用スキルへ固定しない。

## 1. 報告を依頼された単位で新規記事を追加する

新しい報告を依頼されたら、その時点までの関連する内容をまとめ、日付付きの新規記事を追加する。日付が同じでも、別の報告依頼なら別記事とする。

一つの報告依頼に対する執筆中の修正や表示調整は同じ記事に反映する。依頼のたびに無条件で分割するのではなく、「新しい報告」と「現在の記事の修正」を区別する。既存記事への修正が明示された場合はその指示に従う。

小さな実験・条件・図ごとに記事を分割しない。一つの報告に関係する実験は、一つの記事の節としてまとめる。報告依頼がないのに日次の記事生成や自動公開を始めない。

### 日付と識別

- 記事には報告日、題名、短い要約、テーマを持たせる。
- 報告日はユーザーのタイムゾーンで決める。実験日や対象期間が異なる場合は別に記載する。
- 同日記事を区別できるURL・ファイル名にする。既存規約がなければ、`reports/YYYY-MM-DD-topic.html` のように日付と内容を組み合わせ、衝突時だけ連番などを加える。
- 日付だけのファイル名で同日の旧記事を上書きしない。既存記事の日付やURLを一覧整列のために変更しない。
- 訂正メモを追加した日付は報告日と分ける。訂正しただけで新規報告として一覧先頭へ移動させない。

## 2. 過去の記事は当時の記録として残す

新しい結果や異なる結論が得られても、過去記事の本文・結論は基本的にそのまま残す。新しい報告の追加によって古い記事を置換・削除しない。

後から誤りが判明した場合は、該当箇所の近く、または末尾の適切な位置へ訂正メモだけを追記する。本文を正しい値へ黙って書き換えたり、古い図を新しい結果に差し替えたりしない。元の結論と追記が区別できる表示にする。

訂正メモには次を簡潔に書く。

- 誤りが判明した日付。追記日と異なれば両方を区別する。
- どの記述・測定・条件が誤っていたか。
- 結論のどの範囲に影響するか。まだ不明なら不明と書く。
- 訂正を扱う新しい報告があれば、その内容が分かるリンク。

新しい報告がまだない場合は、確認済みの誤りだけを注記する。リンク先を作るためだけに、依頼のない報告を増やさない。単なる追加知見と誤りの訂正も区別する。

過去記事を再生成する構成では、その記事が参照する図・集計値・データも当時の内容を保つ。共有の「最新結果」ファイルへの参照により、本文を変えずに過去の図表だけが更新されないようにする。記事別の保存や版を指定した参照など、既存構成に合う方法を使う。

## 3. 各記事だけで今回の報告を理解できるようにする

目的・比較条件・今回の結論は、毎回の記事に書く。詳しい背景や変更のない手順は過去記事へリンクし、重複を抑える。ただし、今回の結果を理解するためにリンク先の読了を必須にしない。

本文では次を短く再掲する。

- 何を明らかにする報告なのか。
- 何と何を、どの条件で比較したのか。
- 方式名・略語・指標の意味と、結果を読むのに必要な前提。
- 何が分かり、何はまだ言えないのか。

継続調査なら前回からの変更点を明示する。「前回と同じ」だけで比較条件を済ませない。詳しい手順を省略しても、対象の版、主要な条件、比較基準は今回の記事で確認できるようにする。

リンクは「こちら」「前の記事」だけにせず、「測定手順の詳細：日付・記事名」のように、何を参照できるかを示す。必要なら関連節へ直接リンクする。過去の誤った結論を、注記せず今回の前提として引用しない。

記事の長さや章数は内容に合わせる。作業ログの列挙ではなく、目的から結果と解釈へ読み進められる順番にする。

## 4. トップページは新しい順の一覧を基本にする

トップページから各レポートのサブページへ遷移できるようにする。一覧では各記事の日付・題名・短い要約を示し、報告日の新しい順に並べる。同日の順序は作成順などの一貫した基準で決める。

要約は、何を調べ、何が分かった記事かが分かる内容にする。記事を開かないと対象すら分からない「実験報告」「調査しました」のような記載を避ける。

時系列に加え、テーマでも記事を探せる導線を用意する。少数ならテーマ別リンク一覧や見出しで十分。件数が増えた場合はフィルタなどを検討する。検索UIを作ること自体を目的にしない。

テーマ別と日付順の一覧は同じ記事へリンクする。本文をテーマごとに複製しない。テーマ名は既存の分類を優先し、小さな測定条件ごとに増やさない。

各記事から一覧へ戻る導線と、関係する過去・後続記事へのリンクを設ける。横断的なまとめページは必要になったときに追加し、日付付きの報告を置き換えない。

## 5. 実装と確認

既存のサイト構成、記事一覧の生成元、記事とデータの対応を調べてから変更する。表示のためだけに技術基盤を作り直さない。

新規記事と一覧を反映した後、変更範囲に応じて次を確認する。

- 新記事の日付・識別子が正しく、既存記事を上書きしていない。
- 一覧の新しい順、同日記事の順序、日付・題名・要約の対応が正しい。
- テーマから該当記事へ移動でき、一覧への戻り先や関連節へのリンクが有効。
- 目的・比較条件・結論が、過去記事を開かなくても理解できる。
- 過去記事とその図表は、意図した訂正メモなどを除き維持されている。
- 表・図・コード・資料リンクが読み取れ、通常画面・狭い画面・必要な印刷表示に支障がない。

完了時は追加記事へのリンク、今回の要点、必要な訂正追記を短く報告する。新規記事の作成、既存記事の訂正、サイト公開を区別し、実施していない操作を完了扱いにしない。
